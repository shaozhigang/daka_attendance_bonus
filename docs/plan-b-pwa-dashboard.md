# 方案 B：PWA 考勤看板 + 提醒 App

> 自研 Progressive Web App，提供可视化看板、多层提醒与「我已打卡」确认闭环。

---

## 一、产品定位

| 维度 | 说明 |
|------|------|
| 产品名 | 全勤守护 / Daka |
| 形态 | PWA（可添加到手机桌面，类原生体验） |
| 目标用户 | 本人（单用户） |
| 核心价值 | 把 1000 元全勤奖「具象化」，用数据 + 提醒逼近零遗漏 |
| 与方案 A 关系 | **互补**：A 负责系统级提醒，B 负责看板、确认闭环与进度可视化 |

---

## 二、用户故事

1. **作为**需要全勤奖的员工，**我希望**在快漏打时收到多次提醒，**以便**不会忘记打卡。
2. **作为**用户，**我希望**打完卡后点「已确认」，**以便**系统不再催我且记录状态。
3. **作为**用户，**我希望**看到本月全勤进度和日历热力图，**以便**直观感受 1000 元的「倒计时」。
4. **作为**用户，**我希望**每晚自动检查今日是否两次都确认，**以便**漏打时当晚还能补救。

## 四、功能清单与优先级

### P0 — MVP（第一版，1–2 天）

| 功能 | 描述 | 验收标准 |
|------|------|----------|
| 上下班时间配置 | 默认 08:50 / 18:15，可修改 | 设置页保存后立即生效 |
| 多层本地通知 | 按方案 A 时间表推送 | 到点收到通知，点击可打开 App |
| 「我已打卡」确认 | 上班/下班各一个确认按钮 | 未确认时按策略重复提醒 |
| 今日状态卡片 | 显示上班 ✅/❌、下班 ✅/❌ | 一目了然 |
| 添加到主屏幕 | PWA manifest + Service Worker | 可像 App 一样从桌面打开 |
| 本地数据持久化 | IndexedDB / localStorage | 刷新不丢失 |

| 连续全勤天数 | 🔥  streak 展示 |

### P2 — 可选

| 功能 | 描述 |
|------|------|

## 六、提醒策略（与方案 A 对齐）

| 节点 | 时间 | 条件 | 动作 |
|------|------|------|------|
| 上班提醒 1 | 08:30 | 上班未确认 | 普通通知 |
| 上班提醒 2 | 08:45 | 上班未确认 | 普通通知 |
| 上班提醒 3 | 08:52 | 上班未确认 | 强提醒 + 可选震动 |
| 下班提醒 1 | 18:10 | 下班未确认 | 普通通知 |
| 下班提醒 2 | 18:25 | 下班未确认 | 普通通知 |
| 下班提醒 3 | 20:00 | 下班未确认 | 强提醒 |
| 兜底审计 | 22:00 | 任一次未确认 | 红色警报通知 |

**确认闭环逻辑：**

```
到点 → 检查今日该次是否已确认
  ├─ 已确认 → 跳过
  └─ 未确认 → 发通知 → 用户点击「我已打卡」→ 记录时间 → 停止该次后续提醒
```

## 七、技术方案

### 7.1 技术栈

| 层级 | 选型 | 理由 |
|------|------|------|
| 框架 | React + Vite | 开发快，生态成熟 |
| 样式 | Tailwind CSS | 快速出 UI |
| PWA | vite-plugin-pwa | 一键生成 SW + manifest |
| 存储 | localStorage + IndexedDB（idb） | 纯前端，无需后端 |
| 通知 | Web Notifications API | 浏览器原生，需用户授权 |
| 定时 | 前端 Scheduler + Service Worker | 后台触发通知 |

### 7.3 数据模型

```typescript
// 单日打卡记录
interface DayRecord {
  date: string;           // "2026-08-27"
  clockIn?: {
    confirmed: boolean;
    confirmedAt?: string; // ISO 8601
  };
  clockOut?: {
    confirmed: boolean;
    confirmedAt?: string;
  };
  status: 'normal' | 'missed' | 'makeup' | 'rest';  // 正常/漏打/补卡/休息
}

// 用户设置
interface Settings {
  clockInTime: string;    // "08:50"
  clockOutTime: string;   // "18:15"
  bonusAmount: number;    // 1000
  reminderEnabled: boolean;
  reminderStrategy: {
    before20: boolean;
    before5: boolean;
    afterOverdue: boolean;
    auditAt22: boolean;
  };
}
```

### 7.4 通知限制说明

| 平台 | 限制 | 应对 |
|------|------|------|
| iOS Safari PWA | 需用户先「添加到主屏幕」，通知能力有限 | 方案 A 日历作备份 |
| Android Chrome PWA | 通知支持较好 | 作为主提醒渠道 |
| 桌面浏览器 | 可常驻，适合开发调试 | 辅助 |

**结论：** B 与 A **必须同时运行**，B 负责看板与确认闭环，A 负责系统级可靠提醒。

## 九、与方案 A 的协同

| 场景 | 方案 A | 方案 B |
|------|--------|--------|
| 08:30 提醒 | ✅ 日历 | ✅ App 通知 |
| 用户确认「已打卡」 | ❌ | ✅ 停止后续提醒 |
| 全勤进度可视化 | ❌ | ✅ |
| 22:00 审计 | ✅ 日历 | ✅ App 检查 + 红色警报 |

| 月度回顾 | ❌ | ✅ 热力图 |

**推荐：** 两方案同时启用，互为冗余。

## 十一、风险与对策

| 风险 | 对策 |
|------|------|
| PWA 通知在 iOS 上不可靠 | 方案 A 日历必须并行 |
| 用户忘记点「已确认」 | 22:00 兜底 + 强提醒升级 |
| 请假/出差误提醒 | 设置页增加「今日休息」一键标记 |
| 数据丢失 | 定期导出 JSON 备份（P2） |
